## Summary

Learners get one email each time their booking is made, moved, or cancelled. The email uses the mock's templates and carries a calendar invite that adds, moves, or removes the event in their own calendar. Every booking is also copied onto one shared "HOL bookings" Google calendar so admins see the week. Mail is sent by the background worker through the Gmail API as one HOL mailbox. Its Google credential is a service account key (a JSON file from Google Cloud for a robot account allowed to act as that mailbox), uploaded once on the API Keys page as a `GOOGLE` key with the sender mailbox typed beside it. It is stored encrypted and only the worker ever unlocks it. For testing with a personal Gmail (which can't hand its powers to a service account), the same dialog offers **Google sign in** instead: you upload an OAuth client file, click Sign in with Google, approve, and paste back the address Google sends you to; the app keeps a lasting sign in (a refresh token) for that one mailbox. Production can move to the service account later by editing the key. Sending happens after the booking change commits, so a Google outage delays email but never undoes a booking. Admins see each learner's email history on the learner's page.

## Requirements

**User stories**:
- As a learner, I want a confirmation with a calendar invite when I book, reschedule, or cancel, so my calendar always matches my reservation.
- As an admin, I want to set up Google sending once on the API Keys page, with the credential checked as I save it, so a mistake shows at once and not as silent failed mail.
- As an admin, I want to see each email a learner was sent and whether it went out, so I can answer "I never got anything".
- As an admin, I want every booking on one shared calendar, so I can see the week at a glance.
- As the owner, I want the Google credential stored encrypted and unlocked only by the worker, and dev and test bookings never to email real people.
- As the owner, I want to test email from a personal Gmail by signing in with Google in the dialog, and move to a Workspace service account for production by editing the key, with no code change.
- As an admin, I want the API Keys page to tell me when Google stops accepting the credential, so a dead sign in doesn't go unnoticed.

*Queueing (in the booking transaction)*

- **AC-6**: Every booking change that a learner should hear about queues its notices inside the same transaction as the change, in the three functions every caller already goes through: `confirmGuestBooking` (`provisioning` to `confirmed`: kind `booked`), `rescheduleBooking` (`rescheduled`), and `cancelBooking` (`cancelled`, whatever the source: learner, admin, or deactivation). `confirmGuestBooking` changes its `RETURNING` to include `version` (always 1 there, since `bookings_version_bump` skips `provisioning` to `confirmed`) and returns `Result<{ version: number }, "gone">`. Since 2026-10-16 it also takes `shown: { timezone, newAccount }` (`confirmGuestBooking(trx, ref, shown)`): `timezone` is the zone the booking screen used (`GuestBookingInput.timezone`, the account's stored zone for a signed in learner, the form's for a guest), and `newAccount` is the saga's `created` (this booking created the Authentik user, so its welcome job is queued in the same transaction). It hands `shown` to `queueBookingNotice`; `rescheduleBooking` and `cancelBooking` pass none, and their notices take the booking's zone per AC-11 (amended 2026-10-17). Each function queues, through `queueBookingNotice(trx, bookingId, version, kind, shown?)`, in this order: it generates the email id in the app (`crypto.randomUUID()`); inserts one `send_email` job (payload `{ emailMessageId }`, idempotency key `email:<bookingId>:<kind>:<version>`, `ON CONFLICT DO NOTHING RETURNING id`; no row returned means this notice already exists and the function stops); inserts one `email_messages` row with that id and `job_id` (`status = 'queued'`, `booking_version` = the version the change returned, `to_address` = `users.email` now, `subject` per AC-12 or AC-13, `details` = the AC-11 snapshot); then inserts one calendar job (`calendar_upsert` for booked and rescheduled, `calendar_delete` for cancelled, payload `{ bookingId }`, key `calendar:<bookingId>:<version>`). A repeat of the same key inserts nothing. A rolled back change queues nothing. `confirmed` to `completed` and a compensated saga queue nothing. A reschedule always bumps the version, since `rescheduleOwnBooking` already refuses the same start (`same_time`) and any other change moves `starts_at` or `testbed_id`.
- **AC-7**: Google never takes part in the booking transaction. A Google outage, a missing key, or a failed send never refuses, delays, or undoes a booking, reschedule, or cancel; the action's reply is the same as before this feature.

*The job runner (worker)*

- **AC-8**: A new worker step, "jobs", runs after "testbed teardown" each tick. First, an exhausted lease sweep: every handled job that is `running` with `locked_until < now()` and `attempts = 8` (a crash on its last try) is set `failed`. Then it loops: check the budget (stop when 20 jobs have run or 40 seconds have passed, checked **before** each claim so a claimed job is never left to the step timeout), claim one job, run it, record the outcome, until no job is due. A claim is one statement: pick the oldest (`run_at`, then `created_at`) job whose kind is in the handled set, with `attempts < 8` (so the `jobs_attempts_check` cap of 8 is never exceeded), that is either `pending` with `run_at <= now()` or `running` with `locked_until < now()`, `FOR UPDATE SKIP LOCKED`, and set `status = 'running'`, `locked_until = now() + interval '5 minutes'`, `attempts = attempts + 1`. Outcomes: `done` sets `status = 'done'`, `locked_until = null`, `last_error = null`; `retry` sets `status = 'pending'`, `run_at = now() + least(1 minute * 2^(attempts - 1), 1 hour)`, `last_error`; `final`, or a `retry` at `attempts = 8` (a 429 or 5xx on the 8th try included), sets `status = 'failed'` and logs at error level. On **every** path that sets a `send_email` job `failed` (final, attempts used up, the exhausted lease sweep, a missing email row), `finishJob` sets its `email_messages` row to `failed` with the reason in the same transaction, so a dead email never blocks the later ones (AC-10). The handled set is `send_email`, `calendar_upsert`, `calendar_delete`; `send_welcome` jobs are never claimed until feature 16 adds a handler. The daily purge also deletes `done` jobs older than 30 days.
- **AC-9**: At the start of each "jobs" step the worker reads `googleMailConfig`. With no live `GOOGLE` key it claims nothing, logs "jobs: no Google key, email and calendar jobs wait" once per change of state (not every tick), and spends no attempts. A 401 from Gmail or Calendar first drops the cached access token, mints a new one once, and repeats the call once. When Google still rejects the credential (`unauthorized_client`, `invalid_grant`, or `invalid_client` when minting, or a second 401), the breaker trips: that job goes back to `pending` with its attempt given back (`attempts - 1`) and `run_at = now() + 5 minutes`, its `email_messages.last_error` reads "Google rejected the service account key. Check the key and domain wide delegation, and upload a new key on API Keys if needed." (for a Google sign in key, the AC-31 message instead), the step stops for this tick, and the error is logged once per tick. The breaker also marks the key (AC-31).
- **AC-10**: A `send_email` job is not claimable while an older email for the same booking (lower `booking_version`, found through `email_messages.job_id` = the job's id) is still `queued`, so a learner's emails for one booking always go out in version order (booked, then rescheduled, then cancelled), each with its own content.

*Calendar mirror*

- **AC-19**: `calendar_upsert` and `calendar_delete` both run `syncBookingEvent(bookingId)`, which reads the booking's current row (not the snapshot). A missing booking, or one still `provisioning`, is `done` with no call. Event id = the booking id without dashes (valid Google event id characters, so a rerun targets the same event). Calendar ids in URLs are percent encoded. A `cancelled` booking: `DELETE` the event; 404 and 410 count as done. Otherwise (`confirmed` or `completed`): `PUT` the event (update); on 404, `POST` it with that id (insert); a 409 on that insert (a concurrent run created it) retries the `PUT` once. *Invites stay out of the sender's calendar (amended 2026-10-17)*

- **AC-35**: Saving a `GOOGLE` key refuses a Dev inbox or Ops BCC in the sender's own mailbox. "Same mailbox" is the pure `sameMailbox(a, b)` in `lib/email-routing.ts`, a best effort rule: each address is trimmed and lowercased and split at its **last** `@` (as `isTestAddress` does); everything from the first `+` in the local part is dropped; for `gmail.com` and `googlemail.com` the dots in the local part are dropped and the domain reads as `gmail.com`; then local part and domain are compared. So `mnisdm+holops@gmail.com` and `M.Nisdm@googlemail.com` are both in `mnisdm@gmail.com`'s mailbox. The exact sender address is always caught. Workspace aliases and groups, catch alls, and other providers' tag separators can't be seen from the address and aren't caught. The check is the pure `mailboxClash(fields: Stored): MailboxClashError | null` in `server/catalog/api-keys.ts`, with `MailboxClashError = "google_ops_bcc_sender" | "google_dev_inbox_sender"`. A null sender, a null inbox, or a non `GOOGLE` row (whose `Stored` Google fields are all null) never clashes. It checks Ops BCC first, then Dev inbox, and answers one error at a time, so a form with both clashing shows only the Ops BCC message until that is fixed. `google_ops_bcc_sender` is a field error on `opsBcc`, "Use a mailbox outside the sender's account. Every email is already in the sender's Sent folder." (`API_KEY_MESSAGES.opsBccSender`). `google_dev_inbox_sender` is a field error on `devInbox`, "Use a mailbox outside the sender's account, so test invites reach a calendar the way a learner's do." (`API_KEY_MESSAGES.devInboxSender`). It runs in two places with the same function. (1) In both `createApiKey` and `updateApiKey`, `mailboxClash(storedFields(input))` runs **before** `checkCredential`, so a clash costs no Google call. Here the sender is the typed one or the finished sign in's, and an edit with no new sign in has a null sender, which can't clash. (2) In `updateApiKey`, `mailboxClash(after)` runs again inside the transaction, unconditionally (not inside the `ciphertext === undefined` block), right before the `updateTable` write and after the `type_in_use` check. There `after` carries the sender over from the locked row (AC-29). An edit that changes nothing still returns early before (2), so a clashing row is refused only when something is saved, and then it must be fixed. `MailboxClashError` joins both `ApiKeyCreateError` and `ApiKeyUpdateError`, and both `apiKeyError` and `updateError` in `app/admin/actions.ts` map it (their exhaustive switches). For a Google sign in save the code is already spent, so the action returns `restart: true` (the existing `spent` rule, AC-28): the admin signs in with Google again even though the fix is only a field edit. That is accepted, since it is rare and the dialog says which field to fix. The refusal is not audited and writes nothing. The AC-1 helpers gain one sentence each: Dev inbox "… Use a mailbox outside the sender's account.", Ops BCC "Gets a copy of every learner email. Use a mailbox outside the sender's account."
- **AC-36**: At send, `routeEmail` never uses the sender's own mailbox, so a row saved before AC-35 is safe before anyone edits it. `EmailRouting` gains a required `senderEmail: string`; `server/jobs/send-email.ts` already passes `ctx.cfg` (`GoogleMailConfig`, which carries it), so the call site doesn't change. The order: a real address goes to itself, with `opsBcc` as Bcc unless it is null or `sameMailbox(opsBcc, senderEmail)`; the Dev inbox is never looked at, the email is sent as usual, and `sent_to` is unchanged. A test address with no `devInbox` is suppressed as in AC-16. A test address whose `devInbox` is in the sender's mailbox is `suppressed` with `last_error` "The dev inbox is the sender's own mailbox." (`SUPPRESSED_DEV_INBOX_IS_SENDER`), and nothing is sent. Otherwise it is rerouted as in AC-16, never Bcc'd. A learner whose own address is in the sender's mailbox is not changed: that is accepted as an operator only case (only the owner books as the sender, and only their own calendar is at stake).

## Decision

**Chosen option**: Option 2: an outbox in the booking transaction, sent by the worker through the Gmail API as one mailbox, using a domain wide delegation service account key held as a `GOOGLE` API key.

Notices are queued in the same transaction as the booking change and sent later by the worker's job runner. Each one is a single MIME message carrying our own `.ics` invite, rendered with React Email, and sent through Gmail by a service account acting as the HOL mailbox, whose JSON key an admin uploads on the API Keys page. The same key mirrors bookings onto a shared calendar. The owner accepted the domain wide reach of this key for now (2026-10-14); Option 1, a per mailbox grant, is the documented upgrade path.

**Amendment (2026-10-16)**: Option 1 is now built beside Option 2 as the key's second sign in method, because the testing sender (a personal gmail.com) cannot use domain wide delegation. The key holds one method at a time and is switched by editing it. The sign in returns by pasting the `127.0.0.1` address Google opens, because Google redirects only to https or localhost, and dev runs on plain http at a LAN IP. Calls go through `fetch` like the rest of `server/google/`, so the fake fetch covers them; no new dependency.

### State transitions

- `email_messages.status`: (insert) `queued` → `sent` (Gmail 2xx) · `queued` → `suppressed` (test address with no dev inbox, AC-16; booking already ended, AC-18) · `queued` → `failed` (final 4xx, or 8 attempts used). `sent`, `failed`, `suppressed` are terminal. A breaker or retry leaves it `queued`, with `last_error` set.
- `jobs.status` (spec 0001 shape): `pending` → `running` (claim) → `done` | `pending` (retry, breaker) | `failed`. `running` with an expired lease is claimable again.
- `api_keys.google_rejected_at`: null → set (breaker trips, AC-31) → null (a later successful Google call, or a save with a new secret).
- The Google sign in dialog: idle → started (cookie set, link shown) → saved (cookie deleted) or failed (cookie kept when the failure came before the code exchange or the exchange couldn't reach Google, deleted once Google answered it). Starting again replaces the cookie; it expires on its own after 10 minutes.

### Key invariants

- A notice is queued if and only if its booking change commits (same transaction, AC-6); Google is never called inside a booking transaction (AC-7).
- One `email_messages` row and one job per (booking, kind, version) (unique index plus idempotency keys).
- No `send_email` job ends `failed` while its email row is still `queued` (AC-8).
- No job is claimed at `attempts = 8`; `jobs_attempts_check` is never violated.
- A booking's emails leave in version order (AC-10).
- Every email for one booking shows the same zone, the one its booked email used (AC-11, 2026-10-17).
- Only the worker decrypts the `GOOGLE` secret, only through `googleMailConfig` (AC-5). `secret_ciphertext` stays confined to `server/catalog/api-keys.ts`; `os_password` stays confined to `server/catalog/testbeds.ts` (the snapshot read names its columns).
- `last_error` columns hold only fixed app messages and HTTP status numbers, never Google's response body (it can echo request data).
- A test address never reaches a real recipient (AC-16).
- The app never routes a learner's invite to the sender's own mailbox, through the Dev inbox or the Ops BCC (AC-35 at save, AC-36 at send, 2026-10-17).
- The breaker and the no key wait never spend attempts (AC-9).
- One live `GOOGLE` key, with exactly one method, at any time (`api_keys_one_google_uq` plus `api_keys_google_fields_check`). Switching method replaces the secret in the same update, so a key never pairs one method's label with the other's secret.
- A sign in code is exchanged only by the admin whose cookie started it, within 10 minutes, with that sign in's PKCE verifier (AC-27, AC-28). The code exchange always runs after every check that doesn't need Google. The cookie outlives an attempt only while Google hasn't answered its exchange.
- Google sign in is saved only with both scopes granted and a verified sender email (AC-28).
- `refreshToken` and `clientSecret` live only in the ciphertext and in memory in the worker or the saving action (AC-33).

### Security model

- Admins only manage the `GOOGLE` key (`requireAdmin()` on the page and both actions, as in spec 0006 AC-10). The key file is accepted once in a Server Action POST, parsed, encrypted, and dropped; it is never echoed back, and a failed save does not return it (the admin picks the file again).
- The credential is a service account key with domain wide delegation limited to `gmail.send` and `calendar.events`. **Accepted risk (owner, 2026-10-14):** a stolen DB plus keyring could send mail as, and edit the calendars of, any user in the Workspace domain until the key is deleted in Google Cloud. Mitigations: those two scopes only in the delegation entry; the key decrypted only in the worker; rotate it yearly (create a new key, upload it, delete the old one in Google Cloud); optionally set the org policy `iam.serviceAccountKeyExpiryHours` so keys expire on their own. Workspace audit logs show the service account's client ID on every action it takes. The per mailbox grant (rationale Option 1) removes this risk if it is ever needed.
- **Google sign in (2026-10-16).** The refresh token reaches only the one mailbox that signed in, and only for `gmail.send` and `calendar.events`, so a stolen DB plus keyring can send as that mailbox and edit its calendars, not the whole domain's. The owner revokes it in that Google account under *Third party apps and services*. A Desktop app client's secret is not confidential by Google's own design (it ships inside installed apps), so the refresh token is the real secret; both are stored encrypted. The code lands in the admin's own browser at `127.0.0.1`. A program listening on that port on the admin's machine could read it, but can't redeem it without the PKCE verifier, which never leaves the server (the cookie holds it encrypted). The cookie's AAD names the admin, so another admin's session can't use it, and `state` ties the pasted address to this sign in. The consent screen should be **In production** (published): in Testing, Google ends the sign in after 7 days. An app nobody has verified shows Google's "unverified app" warning, which the owner clicks through; it allows up to 100 users, and only one signs in here.
- The worker holds the keyring (already true since spec 0012). The web process holds it to encrypt, and decrypts only its own sign in cookie, never a stored secret.
- The email carries lab links to the learner's own mailbox; the links still require an Authentik sign in inside the booking window (spec 0012). The Ops BCC mailbox receives the same links and should be a restricted internal mailbox.
- Test addresses are rerouted or suppressed, so dev and Playwright never mail outside parties.
- **The organizer's calendar (2026-10-17).** Every invite names the sender mailbox as `ORGANIZER`. If that account's own Google Calendar ever holds a booking's event, Google Calendar owns it and the learner's later updates and cancels stop applying (seen in verify, booking `65b76eb8`). The app keeps its own mail out of that mailbox (AC-35, AC-36), and the HOL bookings mirror is safe, since its events carry Google's own ids and no attendees. What the app can't stop is a person: so nobody accepts or adds a booking invite while signed in as the sender, on any device, and a phone signed in to the sender account doesn't use it as its default calendar. Ops reads the sender's Sent folder or an Ops BCC in another account.
- Key changes are audited (spec 0006 actions); sends are recorded in `email_messages`, not the audit log. No compliance scope; email addresses and names are PII already held in `users`.

### Critical test scenarios

- Happy path: a guest books; the row is `queued` in the same transaction; the worker sends one message whose MIME has the HTML, text, `cid:nile-logo`, and a `METHOD:REQUEST` invite with `SEQUENCE` = version; the row is `sent` with the Gmail id; the calendar event exists. - Rollback: a reschedule that loses its slot (`slot_taken`) queues nothing; a compensated guest saga queues nothing. Verifies **AC-6**

## Migration plan

**Strategy**: switched on by data. Migration `0009` is additive. Until a `GOOGLE` key exists, notices queue and wait and nothing is sent (AC-9), so the code can ship before the owner setup.
**Phases**:
1. Deploy the code and run `npm run db:migrate`; restart the worker so it picks up the new script flags.
2. Owner setup with a `dev-` dev inbox; book, reschedule, and cancel as a `dev-` learner; run the verify.md matrix.
3. Run `npm run calendar:backfill -- --apply`. Real learner emails start with their next booking change.
**Rollback**: delete the `GOOGLE` key (sending stops at the next tick, notices keep queueing), or revert the commit; `0009` needs no down step because the old code ignores the new columns and table.
**Risks**: notices queued before the key exists send late when it is added, minus any whose booking has ended (AC-18). Before phase 2, check that the queued backlog is what you expect. A wrong Ops BCC leaks lab links to that mailbox, so check it on save.

**Amendment (2026-10-16)**: `0010` is additive (two nullable columns, a backfill of `service_account` on existing `GOOGLE` rows, then the widened check under the same name), applied with a `pg_dump` first as usual. Phase 2 can now run with a Google sign in key and a Gmail sender, and production switches by editing the key (see *Configuration required*). **Rollback**: before reverting the code, switch the key to Service account or delete it. The older code parses every `GOOGLE` secret as a service account key, so a Google sign in key would make its jobs step throw "the GOOGLE API key can't be read" each tick. `0010` itself needs no down step.

## Consequences

**Positive**:
- One send path for dev and prod (they share a worker), with no Google env vars and no restart to change settings.
- With the service account: no human sign in, nothing stops working when a password changes, and the HOL address only has to be a real user, not someone's login.
- Bookings never wait on Google; the outbox gives retries and a visible history for free.
- The runner, templates, routing, and Gmail client are what features 16 (welcome) and 17 (reminder) need; each adds a handler and a template.
- Every email lands in the HOL mailbox's Sent folder, a second record beside `email_messages`.
- Email can be tested end to end today from a personal Gmail, with no Workspace admin involved, and production moves to the service account by editing one key.
- Google sign in also works for a Workspace mailbox (if the Workspace allows the app), which gives the per mailbox reach of rationale Option 1 without domain wide delegation; the production choice stays open.
- A dead credential now shows on API Keys, not only on each waiting email.

**Negative / tradeoffs**:
- Mail goes out on the worker's tick, so it lands about 30 to 90 seconds after the action, not instantly.
- If the worker crashes after Gmail accepts a message but before the row is marked, the retry sends a duplicate; Gmail has no idempotency key. Rare, and accepted.
- A leaked key plus keyring reaches every user in the domain for `gmail.send` and `calendar.events`, until someone deletes the key in Google Cloud. Accepted by the owner for now.
- The key never expires on its own; rotation is a manual yearly chore unless an expiry policy is set.
- Setup needs a Workspace super admin (delegation) and possibly an org policy exception for key creation.
- Changing the sender or calendar needs the key file again, because the web process never decrypts.
- Version ordering means one stuck email (backing off for up to about 2 hours) holds back the later emails for that booking.
- Gmail's Workspace limit (about 2,000 messages a day per mailbox) caps volume; far above today's needs.
- The worker no longer runs with the React Server Components condition; any future worker code must not rely on it.
- Google sign in breaks on a password change, a revoke, about 6 months without use, or (while the consent screen is still in Testing) after 7 days, and someone must sign in again by hand, with the client file.
- The paste step is clumsy: a page that won't load, then a copy and paste within 10 minutes. It is accepted because it needs no public https hostname and no callback route.
- Two sign in methods mean two token paths, two breaker messages, and more tests to keep green.
- A personal Gmail sends far fewer messages a day than Workspace (Google publishes about 500 for consumer accounts, against about 2,000), and mail comes from a gmail.com address, which learners may trust less. Fine for testing, a reason to switch before real volume.
- With the invite only as an attachment (AC-15, 2026-10-16), Outlook may show `invite.ics` as a file to open instead of a meeting request with its own bar; the learner opens it to add the event. That is the price of one copy and a body every client shows.
- One zone per booking (2026-10-17) means a later email can differ from the screen that made its change: a returning learner who booked as a guest in India Time reschedules on a signed in screen that shows their stored zone, and the email still says India Time. And a learner who changes their account zone keeps the old zone on that booking's later emails; their next booking uses the new one. Both are rare, and one booking's emails agreeing with each other (and with the calendar invite thread in the inbox) matters more.
- Screens and emails name zones differently on purpose (`GMT+5:30` on the success screen, `India Time` in the email); only UTC is made to match.
- The booking's zone lives in its booked `email_messages` row, so that row is now load bearing: a future purge of `email_messages` (none today, see Neutral) must keep the booked row of any booking that can still change, or its later emails quietly fall back to `users.timezone`. Emails already queued before task 15 keep the zone they were queued with.
- Gmail web lists two `invite.ics` chips on every booking email, because Gmail adds its own inline calendar copy after send (AC-15, 2026-10-17). Learners still get one body, one invite card, and one event; the app can't remove Gmail's copy, and putting the invite back as an alternative would bring back the iOS failure.
- The sender's mailbox check (2026-10-17) sees addresses, not routing: a Workspace alias or group that delivers to the sender passes it. And the app can't stop a person signed in as the sender from adding an invite; that is an operating rule (Security model), not code. An admin who wants the Ops copy in the sender's account must use the Sent folder instead.
- The password box promises a welcome email that only feature 16 sends, the same promise the `/book` success screen already makes (spec 0010); both come true when feature 16 lands.
- The token cache stamp moves from `updated_at` to `secret_updated_at` (AC-30), so the worker's own marker writes don't drop its token. A change that alters who the token acts as always comes with a new secret, so nothing is lost.

**Neutral**:
- `email_messages` keeps rows indefinitely (small); old `done` jobs are purged after 30 days.
- The service account, its delegation entry, and the HOL mailbox become owner managed assets, like the keyring.
