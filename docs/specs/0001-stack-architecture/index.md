## Summary

The reservations app is one Next.js 16 codebase. It runs as Docker containers (a web server, a background worker, and its own Postgres database) from one Compose file in this repo, with the database image pinned to an exact version so a fresh clone behaves the same. The app talks to that database directly over a private Compose network, and the web server is published to the internet through a Cloudflare Tunnel. Everything is dev until rollout (owner decision, 2026-10-24); the database is disposable and can be wiped and rebuilt at any time. A dedicated, self hosted Authentik (on the company AWS instance, `https://authentik.dev.app.nile-global.cloud`) handles every sign in: admins and learners of this app, plus the lab URLs (Nile Portal over SAML, Moodle over OIDC, and Cloudflare Access for the browser based RDP/VNC desktops). Every 30 seconds the worker makes each testbed's Authentik group (made by the owner outside the app) match the bookings. That gives a learner lab access only during their booking: within about a minute of the end, the VMs refuse new requests and sign ins, and Nile and Moodle refuse new sign ins, while a session already open (a VM tab, Nile, or Moodle) may run on until it is closed or that system times it out (spec 0012, 2026-10-15). Email and calendar go through Google APIs.

## Decision

**Chosen option**: Option 1: a self hosted Next.js monolith (web + worker containers) with its own pinned Postgres container, using direct Postgres access, Authentik for all identity, and Google APIs for mail and calendar.

Build one TypeScript codebase. Deploy it as a `web` container and a `worker` container from the same image, next to a pinned `db` Postgres container on a private Compose network, behind Cloudflare Tunnel.

**Implementation skills**: none needed for the database (it is plain Postgres). Project skills: `better-auth-best-practices` (`better-auth/skills`, `.agents/skills/better-auth-best-practices/`) · `shadcn` (`shadcn-ui/ui`, `.agents/skills/shadcn/`) · `tailwind-design-system` (`wshobson/agents`, `.agents/skills/tailwind-design-system/`) · `zod` (`pproenca/dot-skills`, `.agents/skills/zod/`) · `vitest` (`antfu/skills`, `.agents/skills/vitest/`) · `playwright-cli` (`microsoft/playwright-cli`, `.agents/skills/playwright-cli/`) · `playwright-best-practices` (`currents-dev/playwright-best-practices-skill`, `.agents/skills/playwright-best-practices/`)

(basis: the project's own `AGENTS.md`, Kysely over `pg`) |
| Query layer | Kysely over one `pg` Pool per process. Types generated from the live schema with `kysely-codegen` (schemas `hol_app` and `hol_auth`) into `server/db/types.ts`. | A type safe SQL builder with no second schema owner. Better Auth uses the same Kysely/pg path natively. |
| Schemas and access | App tables in schema `hol_app`, Better Auth tables in schema `hol_auth`. Both are owned by the `hol_app` role. `public` has no grants (`revoke all`). RLS stays enabled with no policies on every table (the existing migrations already do this), as a second lock if another role is ever added. The Postgres port is published on `127.0.0.1` only. | The browser never reaching the data is enforced by the network and the database, not only by the app. |
| DB bootstrap | `db/bootstrap.sql` creates the `hol_app` login role (scram password), schemas `hol_app` and `hol_auth` owned by it, `revoke all` from `public`, `create extension btree_gist`, `alter role hol_app set search_path = hol_app, hol_auth, public` (so Kysely, Better Auth, and `migrate` land in the right schemas with unqualified names, and `btree_gist` operators in `public` resolve), and `format('grant connect on database %I to hol_app', current_database())`. Nothing in it names InsForge. It is idempotent. `npm run db:bootstrap` pipes `\set pw '<value>'` and the file over stdin into `docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres -d reservations` as the container's root owned `psql`, so the password is read from its secret file on the host and never appears in git, shell history, or a process list. `npm run db:up` runs it after the container is healthy. It also rotates the `hol_app` password (restart `web`, `worker`, and `npm run dev` after). | A clone needs one command and no manual database setup. One code path, with no dependence on the image's first start hooks (which run as the `postgres` user and cannot read a host owned secret file, and which leave a half built database behind when they fail). |
| DB integrity | Postgres constraints: an exclusion constraint so a testbed's booking time ranges never overlap (`btree_gist`), and uniqueness rules modeled in feature 3. Multi row changes (book, reschedule as one swap, cancel) run in one Kysely transaction. | Double booking is impossible even under races. Note for feature 3: "one Upcoming/Current booking per learner" depends on the clock, so it needs an explicit status or end time rule, not a `now()` index predicate. |
| Migrations | Plain SQL files in `db/migrations/` (`NNNN_name.sql`), applied forward only by a one shot `migrate` compose service before `web`/`worker` start. Runner: Kysely's `Migrator` with a small custom `MigrationProvider` that reads the `.sql` files (each file runs in one transaction; no `concurrently` statements), `migrationTableSchema: 'hol_app'`, run as `hol_app`. Only the `migrate` service runs migrations, never `npm run dev`, and `scripts/deploy.sh` takes a `pg_dump` right before each run. Better Auth's tables are generated once with its CLI and committed as a migration. A rollback of the image never rolls back the schema, so migrations stay backward compatible for one release. | Reviewable in PRs, with a deterministic order at deploy. |
| Identity provider | Self hosted Authentik, **dedicated to HOL**, on the company AWS instance at `https://authentik.dev.app.nile-global.cloud` (public URL behind company proxy/LB), version pinned. **That one instance serves every clone of this repo**, so it is the only shared system (see *Environments*). The lab's own Authentik (`authentik.nile.global`) is not used by the app. | Owner decision. It holds every admin and learner and protects every lab URL. Its public URL is the OIDC issuer for both the browser and the server. |
| App sign in | Better Auth with the `genericOAuth` plugin against one Authentik OIDC application (authorization code + PKCE). **Database sessions** in schema `hol_auth` through the shared pg Pool. `session.expiresIn` 8 hours, cookie cache **off**, so every request checks the session row. `trustedOrigins` = `APP_URL`. | Deactivation or a role change ends access at once by deleting session rows. There are no cookie size limits. Role mapping from the groups claim is settled in the feature 4 spec. |
| Authentik API client | `@goauthentik/api` (official generated TypeScript client), pinned to the deployed Authentik version, wrapped in `server/authentik/` with a 10 second timeout and retries for safe reads only | Typed, and matches the server. Runner up: a thin hand written `fetch` wrapper (about 10 endpoints are used). |
| Authentik keys | **Master key**: used only by `npm run authentik:setup`, an idempotent script that creates or updates the app's OIDC provider and application and prints the client id and secret. It is run by the owner from their machine or the host, with the master token passed for that run only. It is never loaded by `web` or `worker`. **Provisioning key**: the token of a service account with a limited RBAC role, used for all runtime user, group, and session calls. | The scope rule. The RBAC role, and the fallback if Authentik cannot stop the token from touching admins, are settled in the feature 4 spec. |
| Lab access model | One Authentik group per testbed, made **outside the web app** by the owner and marked with the attribute `hol_testbed_group = true`. The admin types the group's exact name (the testbed's Group Name) in the console, and the app refuses a name that does not exist or is not marked (spec 0017, 0018). The app never creates, renames, or deletes a group. The worker's **access reconciler** adds and removes members. The **owner binds** each group to the lab's Authentik applications by hand. Every group write passes a guard that refuses to add anyone to an unmarked group. | Engineer's pick (least API rights). The marker stops the token being used to add anyone to an admin or unrelated group, and a typo can never reach one. |
| Access reconciler | Every worker tick (30 seconds): compute the desired members of each testbed group from the bookings active at DB `now()` (Current, and not cancelled), read the actual members from Authentik, then add the missing ones and remove the extra ones. For each removal, also delete the learner's Authentik sessions and call Cloudflare Access revoke. | A state based sync recovers by itself after a crash, a missed tick, a reschedule, or a cancel. Cancel and deactivation also trigger an immediate reconcile run so the cut off is instant. |
| Background jobs | A `jobs` table: `kind`, `payload`, `run_at`, `status` (`pending`, `running`, `done`, `failed`), `attempts`, `locked_until` (a lease), `last_error`, and a unique `idempotency_key`. The worker claims due rows in a transaction (`FOR UPDATE SKIP LOCKED`, setting `locked_until = now() + 5 min`). A crashed job's lease expires and it is retried. Exponential backoff, at most 8 attempts, then `failed` (logged at error level and shown in the console). Handlers re read current state and skip stale work (e.g. a reminder for a cancelled booking). Used for emails, calendar mirror writes, and reminders. Access is not a job; the reconciler owns it. | A database backed queue first: nothing extra to host. |
| Provisioning saga (guest booking) | 1) One transaction inserts the booking as `provisioning` (it holds the slot under the constraint). 2) Find or create the Authentik user by email. An existing user is reused without changing any of their attributes, and an existing admin is refused with a generic error. 3) Link the user and mark the booking `confirmed`. On failure: delete the booking, and delete the Authentik user only if this attempt created it. A worker **sweeper** runs the same compensation on any `provisioning` booking older than 10 minutes (a crash in the middle). | No orphan user and no stray booking, even if the process dies between steps. Group membership needs no saga step, because the reconciler adds it at start. |
| Worker process | Single replica. `worker/index.ts` bundled with esbuild to `dist/worker.js` in the same image, with `server-only` aliased to an empty stub module. On SIGTERM it finishes its current job and exits. One loop each tick: reconcile, sweep, claim jobs, purge expired rate limit rows (daily). | The Next.js standalone build has no separate process. A single replica keeps the reconciler simple. |
| Email sending | Gmail API (`@googleapis/gmail`). The credentials live on the `GOOGLE` API key (spec 0013), with two sign in methods: Google sign in (a personal Gmail, for now) or a Workspace service account with domain wide delegation for `gmail.send` and `calendar.events`. The refresh token is stored encrypted in the DB. | The same HTTPS send code either way. Only the credentials differ, and they are edited in the console. |
| Email content | React Email components rebuilt from the two standalone HTML files in `context/`, sharing the header, details card, and footer. Raw MIME built with nodemailer's `MailComposer` (HTML + text + `icalEvent`). `.ics` built with `ical-generator`: `ORGANIZER` is the sending mailbox, `UID` is `<booking id>@<APP_URL host>`, and `SEQUENCE` is the booking's version number, with `METHOD:REQUEST` on book and reschedule and `METHOD:CANCEL` on cancel. Every learner email BCCs `HOL_OPS_BCC`. The **set password / welcome email** is sent by the app the same way: the app gets a recovery link from Authentik's API and puts it in our template (Authentik needs no SMTP). | One message per change carries both the Nile template and the invite (scope rule). One sender, one look, and the send status is visible in the console. |
| Calendar | Google Calendar API (`@googleapis/calendar`) mirrors each booking onto one shared "HOL bookings" calendar (shared with the impersonated mailbox), with **no attendees** and `sendUpdates=none`, as an idempotent job keyed by booking id. The event id is stored on the booking. | An admin week view without Google sending its own invite emails to learners. |
| Bot protection | Cloudflare Turnstile on the guest Step 1 form, verified on the server before any Authentik call (Cloudflare's "always passes" test keys until a real widget is set up). Database backed rate limits keyed by `CF-Connecting-IP` (trusted only because the tunnel is the sole ingress) and by email: 5 booking attempts per IP per 10 minutes, 3 per email per hour. | Guest booking creates real Authentik users without sign in, so it must not be scriptable. |
| Secrets at rest | App level AES-256-GCM (`node:crypto`), ciphertext format `v1:<keyId>:<iv>:<tag>:<ciphertext>`, and a keyring so keys can be rotated. Covers API key secrets and the Gmail refresh token. | The database only ever stores ciphertext. Small and fully under our control. |
| Config and secrets | Plain settings come from env. Secrets come from files mounted by compose `secrets:` (with plain compose these are bind mounted, root readable files, not a vault), read through a `NAME_FILE` convention. `server/env.ts` holds a Zod schema per process (web, worker, migrate). It is parsed lazily when the process starts, **never during `next build`**, so the image builds without production values. | Bad config fails fast at start. The image stays environment free. |
| Repo layout | `app/` (routes) · `components/ui/` (shadcn) · `components/` (app components) · `server/` (services, `db/`, `authentik/`, `email/`, `jobs/`, `access/`, `env.ts`; every module imports `server-only`) · `worker/` (entry) · `emails/` (React Email) · `lib/` (code safe on both sides: Zod schemas, time helpers) · `db/bootstrap.sql` · `db/migrations/` · `scripts/` (`authentik-setup.ts`, `seed-dev.ts`) · `docker/`. Path alias `@/*` to the repo root. | Clear server/client boundaries, with web and worker sharing `server/`. |
| Container image | A multi stage Dockerfile on `node:24-slim`. It runs as a non root user, copies the standalone output plus `.next/static` and `public`, plus `dist/worker.js` and `db/migrations`. `HOSTNAME=0.0.0.0`, `PORT=3000`, `TZ=UTC`. Healthcheck on `/api/health`. | One image for all three services. |
| Hosting | On prem Docker host. A compose project with `migrate` (runs once), `web` (`node server.js`), `worker` (`node dist/worker.js`), and the `db` Postgres container. `web` is reached through the host's existing Traefik (the Cloudflare Tunnel sends the hostname to Traefik, and Compose has no `cloudflared` service). `db` and `migrate` sit on a Compose created network `hol-internal`; `web` and `worker` also join the host's `traefik` network for ingress and outbound calls. `docker compose up -d --wait db` works alone on a machine with no Traefik. | Owner decision (no Vercel Pro). Co located with the database. |
| Ingress | The Cloudflare Tunnel sends the app hostname to the host's Traefik, which routes to `web:3000`. The database is never published beyond `127.0.0.1`. Authentik is reached outbound at its AWS public URL. | No open inbound ports. It matches how the lab VMs are already exposed. |
| CI/CD | GitHub Actions on push to `main`: lint, typecheck, unit tests, build image, push to GHCR tagged `sha-<commit>` and `main`. Deploy is a manual `scripts/deploy.sh` on the host (`docker compose pull && docker compose up -d`, which runs `migrate` first). | Route gating | `proxy.ts` lets public routes through (landing, guest booking, auth callbacks, health) and requires a session for learner routes and admin routes. The unlisted admin entry path comes from `ADMIN_ENTRY_PATH` (default `/l0gin`). Admin pages send `X-Robots-Tag: noindex`. Real authorization runs again in every Server Action and page (feature 4). | Coarse and cheap. Never the only check. |
| Observability | pino JSON logs to stdout (read via `docker logs`), with a request id or job id on every line and redaction of secrets and tokens. Error monitoring stays **Deferred** (scope). | Searchable from day one. No new service. |

| Environments | **One environment: dev** (owner decision, 2026-10-24). Everything is dev until rollout. At rollout the data is cleaned and a production setup is stood up, which is a later decision with its own spec. ### Database container

The `db` service in `docker/compose.yaml` is the only place the database version is chosen. A fresh clone gets exactly this Postgres.

| Part | Decision |
|---|---|
| Image | `postgres:18.6-bookworm@sha256:bbf83594798e144bff365a9c191c5d779f181fb3135902064ab8ff11918020fc`. Tag for people, digest for the machine. The digest is the multi architecture index digest (checked with `docker buildx imagetools inspect`, media type `oci.image.index`), so x86 and Apple Silicon clones both resolve. Debian based (not Alpine) so text sorting (collation) behaves like the usual Postgres on Linux. PostgreSQL 18 is a current major with years of support left. Runner up: 17. (basis: boring technology, pin what you run) |
| Storage | Named volume `hol_pgdata` mounted at `/var/lib/postgresql` (the PostgreSQL 18 image keeps its data in a per major folder below that; `PGDATA` is not overridden). Removing the volume resets the database. |
| Database and roles | `POSTGRES_DB=reservations`. Superuser `postgres` with its password from the `postgres_password` secret through `POSTGRES_PASSWORD_FILE`. The superuser is used only by the container and `db:bootstrap`. The app uses `hol_app` only. Local socket connections inside the container are trusted by the image, which is why `docker compose exec db pg_dump -U hol_app` needs no password. |
| Port | Published as `127.0.0.1:${DB_HOST_PORT:-5432}:5432`. `DB_HOST_PORT` is only the host side; the container side is always 5432, and `DATABASE_PORT` stays the port the app connects to (`DB_HOST_PORT` from the host, 5432 from a container). Containers use `db:5432` on `hol-internal`. `hol-internal` is a normal Compose bridge created by this project (no `external: true`, no `internal: true`), because Docker does not publish ports for containers on an internal only network. The host's `traefik` network stays `external: true`. |
| Health | `pg_isready -h 127.0.0.1 -d reservations`. The TCP address matters: during first start the image runs a temporary server with a socket only, so a socket check can pass too early. `migrate` has `depends_on: db: condition: service_healthy`, and `web` and `worker` follow through `migrate`. |
| Secrets and where they live | `SECRETS_DIR` defaults to `../.secrets` in `docker/compose.yaml` (`${SECRETS_DIR:-../.secrets}`, `/.secrets` is gitignored). `docker/.env` is read if it exists (`env_file` has `required: false`) and overrides it. `db:up` reads `SECRETS_DIR` from `docker/.env` when present, else the default, and creates `postgres_password` and `hol_app_password` if missing: 32 random bytes as hex, mode 600 (hex avoids quote and backslash problems in the `\set` line). `.env.example` points `DATABASE_PASSWORD_FILE` at the same file. The builder must confirm that `docker compose up --wait db` does not demand the app only secrets (`auth_secret` and the others); if it does, `db:up` creates empty placeholders for them or the app secrets move to a profile. |
| Bootstrap | `db:up`: ensure secrets, `docker compose up -d --wait db`, then `db:bootstrap` (see *DB bootstrap*). `scripts/deploy.sh` runs the same bootstrap before `migrate`, so a rotated password is applied. A bare `docker compose up` with no bootstrap fails at `migrate` with a clear login error, which is the accepted cost of one code path. |
| One clone per host | `name: reservations` stays, so one clone per host. A second clone sets `COMPOSE_PROJECT_NAME` and its own `DB_HOST_PORT`. `db:reset` removes the volume through Compose (`docker compose down -v db`), never by a hard coded volume name, and keeps the secret files so `.env.local` stays valid. |
| Upgrades | Minor and digest bumps: change the pin in one commit, then `docker compose up -d db`. A **major** bump is a dump and restore into a new volume, never a tag change. Dependabot's `docker-compose` ecosystem for `/docker` proposes the digest updates (the `docker` ecosystem only reads Dockerfiles). |
| Backup | `scripts/deploy.sh` runs `docker compose exec -T db pg_dump -U hol_app -d reservations -n hol_app -n hol_auth -Fc` before each `migrate`. Restore steps live in the README. |
| Cross platform | Add `.gitattributes` (`*.sh`, `*.sql` with `eol=lf`) so Windows checkouts do not break scripts. The `db:*` commands are tsx scripts that call `docker` (not bash). |
| What a clone still sets up by hand | Only the database is automatic. Authentik (client, provisioning token), the encryption keyring (`npm run secrets:keygen`), and `AUTH_SECRET` are still created by the owner, as the README describes. |

Commands a clone uses, in order: `npm run db:up` (secrets if missing, start `db`, wait until healthy, bootstrap), `npm run db:migrate`, then `npm run dev`. `npm run db:reset -- --yes` (the extra `--` passes the flag through npm) drops the volume and runs `db:up` again, and refuses without `--yes`. New `package.json` scripts: `db:up`, `db:reset`, `db:bootstrap`; no existing script changes (codegen and tests read the same `DATABASE_*` env).

**Cutover on this host.** Port 5432 is held by InsForge today. The first step is to stop InsForge's containers (the data is disposable and the downtime is accepted), start `db` on 5432, migrate, redeploy, and verify. InsForge's removal is the last step (see *Done when*).



**Done when** (what `/develop` builds and `/check verify` proves):

- From a fresh clone with Docker only, `npm run db:up && npm run db:migrate` leaves a healthy database with the `hol_app` role, both schemas, `btree_gist`, and every migration applied, even when `docker/.env` does not exist. No step names InsForge.
- `docker compose config` shows the image with the exact tag and digest above, and no other service or file in the repo references `insforge`, `insforge-postgres`, `insforge.internal_schemas`, or PostgREST (files that record history may: this spec's rationale, `docs/.agent-cache/`, and `docs/reviews/`).
- `npm run db:reset -- --yes` returns to the same state as a fresh clone, and `npm run db:codegen -- --verify` and `npm test` pass against it.
- `scripts/deploy.sh` produces a restorable dump through `docker compose exec`, and `migrate` runs before `web` and `worker`.
- `docker compose -f docker/compose.yaml up -d --wait db` works on a machine with no `traefik` network, and `docker compose config` shows `hol-internal` as a project network with no `external: true`.
- `db:bootstrap` run twice in a row succeeds both times, and a wrong `hol_app` password is replaced by the file's value.
- The words dev and production no longer describe two environments anywhere in the README, `AGENTS.md`, `.env.example`, `docker/compose.yaml`, `scripts/deploy.sh`, code comments, or the specs this amendment touches (the Google key's service account versus Google sign in choice in spec 0013 and the rollout plan stay as written).
- Existing InsForge data is dropped, not migrated. The owner authorized removing InsForge completely (2026-10-24), including its containers, volumes, images, and the `~/insforge` directory on this host. That removal runs **last**, only after the new `db` is healthy, migrated, and the app is verified against it, and a final `pg_dump` is kept in `~/backups`. Two things outside the host stay with the owner because they change shared systems: the Authentik application and provider that gate `insforge.nile.global` on the lab Authentik, and its Cloudflare tunnel route. The build lists them and does not touch them.

### Build invariants (every later spec and build must honor these)

- The browser never reaches the database or the Authentik **management** APIs. All of it goes through `server/` modules marked `import 'server-only'`. (The browser does visit Authentik for sign in and set password pages.)
- The master Authentik key is never in the `web` or `worker` environment.
- Every Authentik group write goes through the guard, which only allows adding a member to a group marked `hol_testbed_group`. No code creates, updates, or deletes a group.
- All timestamps are stored as UTC `timestamptz`, with DB `now()` as the clock for scheduling. Display converts to the viewer's IANA zone (learner: their chosen zone; admin: their own zone).
- No overlapping bookings per testbed is enforced by a Postgres exclusion constraint, not only by app checks.
- Steps that touch Authentik and the DB together follow a persisted saga with a sweeper (as above), never a compensation held only in memory.
- Lab access membership is owned by the reconciler alone. No other code adds or removes testbed group members.
- Authorization is re checked in every Server Action and protected page through one shared helper (`server/auth/require.ts`), never by hand per action. A test asserts every Server Action calls it.
- Secrets are written only. No code path returns a decrypted secret to the browser.
- Email or calendar failure never rolls back a booking change. It is a retried job, and its status is visible to admins.
- If Authentik is down, sign in and guest booking fail with a clear "try again shortly" message, and the reconciler retries on its next tick. Existing bookings are untouched.

Plain env:

- `CLOUDFLARE_ACCOUNT_ID`: for Access revoke
- `TURNSTILE_SITE_KEY`: guest form widget
- `WORKER_ENABLED`: `true` only on the `worker` container, and on one machine at a time (see *Environments*)
- `LOG_LEVEL`, `NODE_ENV`, `TZ=UTC`, `PORT`, `HOSTNAME`

Secret files (`*_FILE`):
- `AUTH_SECRET_FILE`: Better Auth secret
- `AUTHENTIK_CLIENT_SECRET_FILE`: the app's OIDC client secret
- `AUTHENTIK_PROVISIONING_TOKEN_FILE`: runtime service account token
- `DATABASE_PASSWORD_FILE`: `hol_app` password
- `POSTGRES_PASSWORD_FILE`: the `db` container's superuser password (used only by the container and its first start bootstrap, never by the app)

- `TURNSTILE_SECRET_KEY_FILE`: guest form verification
- `AUTHENTIK_MASTER_TOKEN`: passed only to the setup script for one run, never stored with the app

## Consequences

**Positive**:
- One codebase and one image. Web and worker share every service module, so there is no drift between "what the UI does" and "what the job does".
- Double booking is impossible at the database level, and multi step writes are real transactions.
- Lab access heals itself: whatever happened before, each tick makes the groups match the bookings.
- Deactivation ends app sessions at once (DB sessions).
- No inbound ports are open. Every lab URL and the app share one identity, and one learner username works everywhere. Nothing is paid beyond existing infrastructure.

**Negative / tradeoffs**:
- The team operates the Docker host, the Postgres container, backups, and upgrades. There is no managed platform to lean on.
- Open Nile Portal and Moodle sessions survive the end of a booking until those systems' own timeouts. An open VM tab can survive it too, with no guaranteed bound, because Cloudflare doesn't close an open browser rendered stream (spec 0012, 2026-10-15). No lab system gets a hard cut of an open session.
- The Postgres image is pinned by tag and digest, so nothing changes under you. The cost is that updates are deliberate: Dependabot proposes a new digest or minor, and a **major** version is never an image bump (the data directory layout is per major), it is a dump and restore.
- The reconciler makes Authentik API calls every 30 seconds (one membership read per testbed). That is fine at this scale, but it grows with the testbed count.
- A single worker replica is a single point of delay: if it is down, access changes and emails wait until it is back (nothing is lost).
- Several integration facts are unconfirmed (see Follow-up) and must be proven before later features rely on them.
- Every clone shares one Authentik. A test run can create real Authentik users and, with a worker on, change real group membership, so test users are `dev-` prefixed, only one worker runs across all clones, and the Authentik write boundary holds. The database itself carries no such risk: it is disposable until rollout.
- The data lives in a Docker volume on one host. `scripts/deploy.sh` dumps before each migration, but until a nightly off host dump exists (Follow-up), losing the volume loses the data. That is accepted while everything is dev.
- The owner makes and marks each testbed group, and binds it to its Authentik applications, by hand, so a new testbed is not fully live until those manual steps are done. The admin then types the group's exact name in the console.

**Neutral**:
- `proxy.ts` (not `middleware.ts`) is the Next.js 16 convention.
- Nothing here depends on InsForge any more. If a feature beyond Postgres (file storage, functions) is ever needed, decide it in its own spec.
