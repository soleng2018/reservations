## Summary
Spec 0029 opens lab access 5 minutes before `starts_at`. One shared constant, `ACCESS_LEAD_MS`, sets both the reconciler's desired set and the portal reset's `START_MARGIN`. The learner copy and the emails are updated, and the change comes with DB tests for the reconciler, the stop check, and the held run check. The core change is small, correct, and well tested. The main problem is outside the diff. The rule that decides whether a cancel or move "was Current" (`starts_at <= now()`) still ignores the lead. A learner who has early access and cancels or reschedules inside those 5 minutes therefore gets no portal reset and no cleanup hook, even though they had the tenant and the VMs.

## Major

### 🟠 A cancel or move during early access queues no portal reset and no cleanup hook, `server/db/bookings.ts:108` and `server/db/bookings.ts:184`
**Problem**: `rescheduleBooking` and `cancelBooking` compute `was_current` as `starts_at <= now()`. That decides whether to queue `queuePortalReset` (spec 0023 AC-3) and `queueCleanupNotice` (spec 0021). Since this change, the learner is in the testbed group and the type group from `starts_at - 5 min` (`server/worker/reconcile.ts:253-257`), so they can sign in to the Nile Portal and the clients for up to 5 minutes before `was_current` turns true. If they (or an admin, or the deactivation sweep) cancel or move the booking in that window, `was_current` is false. Nothing is queued. The booking never reaches `ends_at` as confirmed, so `queueEndedRuns` never picks it up either.
**Why it matters**: The tenant and the VMs can be left with that learner's changes for the next learner on the testbed. That breaks the owner story in spec 0029 ("nobody sees a half cleaned tenant") and the reason for spec 0021/0023. Spec 0029 AC-2 says the cleanup hook "keeps `starts_at`", but it does not seem to have considered that access now starts before it. This is a gap in the spec, not just in the code.
**Suggested fix**: Decide it in the spec first (spec 0029 AC-2 needs amending, through /architect). Then compute `was_current` with the same lead (`starts_at <= now() + ACCESS_LEAD`) in both functions, or compute it with a shared SQL fragment so the reconciler and these two cannot drift. Add a test: a cancel and a move of a booking starting in 4 minutes each queue a reset (and a cleanup job when the key is live), and one starting in 6 minutes queues neither. `bookingPhase` metadata and `manage.ts:174` (`current`, display only) can stay as they are.

## Minor

### 🟡 The buffer between "reset stops" and "learner gets in" is now zero, `lib/portal-reset/timing.ts:12`
**Problem**: Before this change, the reset stopped 2 minutes before access opened (margin 2 minutes, access at start). Now both happen at the same instant: `START_MARGIN = ACCESS_LEAD_MS`. The stop check runs only before each call and step. So a step or write already in flight (one call can take up to `ATTEMPTS` x `CALL_TIMEOUT` plus backoff, about 68 s, and a `wait` part longer) can keep writing after the reconciler has added the next learner. The reconciler and the engine also run on separate ticks.
**Why it matters**: It is unlikely at today's 1.2 to 1.7 minute runs, but the invariant "a run never writes while a lab is Current or starting within N" no longer leaves room before access opens.
**Suggested fix**: Consider `START_MARGIN = ACCESS_LEAD + 2 min` (an 18 minute window, still about 10 times the measured need), or record in spec 0029 that the zero buffer is accepted. The timing test that ties `TARGET` to `GAP - START_MARGIN` would need adjusting.

### 🟡 The back to back test does not test back to back, `server/worker/reconcile.test.ts:119`
**Problem**: The first booking ended an hour ago (`-2, -1`), so this repeats the existing "ended learner removed" case. Spec 0029's critical scenario is a first booking whose `ends_at` has just passed and a next booking starting 25 to 30 minutes later on the same testbed, with neither learner in the group before the lead. The line `expect(first.user.id).not.toBe(next.user.id)` asserts only fixture setup.
**Suggested fix**: Put the first booking's end at `now() - 1 minute` and the next start at `now() + 4 minutes` (the gap constraint allows this only with the half hour rule dropped, which the test already does, or with the gap tested at its real 30 minutes). Also add a case where the next start is 6 minutes away and the group is empty.

### 🟡 The DDL scan does not see raw `alter table`, `tests/ddl-lock-scan.test.ts:10`
**Problem**: The four new tests correctly run `alter table ... drop constraint bookings_starts_on_half_hour` inside `inRollbackDdl`. But `DDL_HELPERS` matches only `applyBookingGapMigration(` and `restoreOldOverlapRule(`, so a later copy of this pattern in plain `inRollback` would pass the scan and starve the other DB test files.
**Suggested fix**: Add a small helper such as `dropHalfHourRule(trx)` to `server/db/testing.ts` and register it in `DDL_HELPERS`, or match `/alter table/i` in the scan. The helper also removes the four copies of the same SQL.

### 🟡 Stale "Current" wording in the reconciler docs, `server/worker/reconcile.ts:38`
**Problem**: The header comment and `server/worker/AGENTS.md` ("Desired members are active learners with a confirmed booking that is Current by the DB clock") now understate the rule: a booking counts from `starts_at - 5 min`.
**Suggested fix**: Say "Current, or starting within `ACCESS_LEAD` (spec 0029)". `/sync` can do the AGENTS.md line.

## Strengths
- One constant feeds the reconciler SQL, `stopCheck`, and `settleHeldRuns`. The timing test pins `START_MARGIN === ACCESS_LEAD_MS` and the 20 minute window, so the two sides cannot drift silently.
- The new DB tests use the database clock throughout (`now() + interval`), test both sides of the boundary (4 vs 6 minutes) for the testbed group, the type group, the stop check, and the held run, and correctly use `inRollbackDdl` for the DDL.
- The import of `lib/lab-access.ts` into `lib/portal-reset/timing.ts` is safe. That module has only type imports and no `server-only`, so nothing new enters the worker bundle.
- The quoted printable decoder is correct: it removes soft breaks first, decodes hex in a single pass so a decoded `=` is not re-read, and rebuilds UTF-8 through a latin1 buffer. It has focused tests.
- Learner overlap is safe: the 30 minute per testbed gap means the next learner joins 25 minutes after the previous one is removed, and a learner can have only one live booking, so their own bookings cannot collide.

## Test coverage
Well covered: the reconciler's lead for the testbed group and the type group, the stop check margin, the held run margin, the timing invariants, the copy (the units, the email snapshots, e2e), and the MIME decoder. Not covered: the cancel and reschedule path during the early window (the Major above), a true back to back handover, and the exact 5 minute boundary.
